**Workflow**: Remain on main; never create a branch whose name contains codex.
**Tests**: Mandatory. A task labelled **RED** adds one public-seam test for one missing observable behavior and proves the expected failure through the configured harness. Its next **GREEN** task supplies only the minimum coherent behavior required for that test. Setup, migration bookkeeping, and acceptance-evidence tasks are not artificial RED/GREEN pairs.
**Verification**: .\harness.cmd is the sole setup and verification interface. No task may use a separate user-facing restore, build, test, or migration workflow.

## Task protocol

Every checklist item gives its dependencies, public seam, canonical harness verification, observable Done condition, and requirement traceability. [P] appears only when completed dependencies make the listed files independent of other in-progress tasks. PostgreSQL integration tests may verify database constraints and permissions because those constraints are public durable behavior; unit tests must not target private parser, controller, or EF implementation details.

## Scope and Architecture Guards

- Do not introduce microservices, a message bus, CQRS/event-sourcing framework, generic workflow engine, SPA framework, external scheduler, production identity provider, notification provider, external connector, or formula eval/Roslyn/generic expression engine.
- Preserve Kpi.Web -> Kpi.Application -> Kpi.Domain; permit Kpi.Infrastructure.Postgres -> Kpi.Application + Kpi.Domain; never permit Domain to depend on Web/EF/PostgreSQL/delivery.
- Preserve .NET 10/C# 14, MVC, EF Core/Npgsql, PostgreSQL, server-rendered UI, progressive minimal JavaScript, canonical invariant Decimal string snapshots, and separate migration/runtime database roles.
- Schema migrations contain no product/demo seed data. Development-only idempotent seeding is T053-T054 and never runs in Production.
- The specification remains unchanged in this task-generation step; its status metadata is not modified here.
